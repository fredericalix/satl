# Docker Engine API compatibility, intentional deviations

Every intentional deviation from Docker Engine API v1.43+ semantics gets an entry here,
in the same PR that introduces it (CLAUDE.md invariant #8). Target semantics: Docker
Engine API v1.43 (negotiable down to 1.24). Verified against docker CLI 29.4.2.

## Daemon-wide (M0)

| Area | Deviation | Since |
|---|---|---|
| Swarm lifecycle | SatL self-initializes a single-node cluster on first boot: `/info.Swarm.LocalNodeState` is `active` and `ControlAvailable` is `true` from day one (Docker defaults to `inactive` until `swarm init`). `swarm init` will still exist for options (M2). | M0 |
| `/info.Swarm` | `NodeAddr` empty and `RemoteManagers` null until M2 introduces advertise addresses and the manager list. | M0 |
| `/_ping` headers | No `Builder-Version` header (no BuildKit); `Docker-Experimental` always `false`. | M0 |
| `Server` header | `Server: SatL/<version>` instead of `Server: Docker/<version> (linux)`. | M0 |
| `/version` | No `GoVersion` / `Experimental` fields (SatL is not Go; the docker CLI renders the missing field as empty). | M0 |
| `/info` | Minimal coherent v1.43 subset: `LoggingDriver`, `RegistryConfig`, `Plugins`, cgroup/runtime fields, etc. are absent. `Driver` is always `zfs`. Counts come from the daemon; zero on a daemon whose backend is not wired. | M0 |
| Version negotiation | Error text for a too-old client omits Docker's trailing "please upgrade your client to a newer version". Single-component prefixes like `/v1/_ping` are treated as normal (unknown) paths → 404, where Docker parses `1` as a version → 400. | M0 |
| Errors | Wrong HTTP method on a known path returns an empty-body 405 (Docker returns a JSON error body). `501 Not Implemented` is used for "not implemented yet" where Docker would typically answer 400/500. | M0/M1 |

## Container model (M1)

| # | Deviation |
|---|---|
| 1 | **A Docker "container" is a SatL Task.** `Id` is the 25-char base36 Task ID (not 64 hex); `Names` is `["/<service name>"]`. |
| 2 | `State`/`Status` are derived from the task state machine: `new`…`ready` → `created`; `starting`/`running` → `running`; `complete`/`shutdown`/`failed` → `exited`; `rejected`/`orphaned` → `dead`. `paused` and `restarting` never occur; `Paused`, `Restarting`, `OOMKilled` are always false. |
| 3 | `?name=` must satisfy SatL's *service* naming rule (`^[a-zA-Z0-9](?:[-_]*[A-Za-z0-9]+)*$`, ≤ 63 chars), dots are rejected, unlike Docker's `[a-zA-Z0-9][a-zA-Z0-9_.-]*`. |
| 4 | Unsupported host options are **rejected with 400**, never silently ignored: `Privileged`, `CapAdd`/`CapDrop`, `SecurityOpt`, `Devices`, `CgroupParent`, `Sysctls`, `Ulimits`, `PidMode`/`IpcMode`/`UTSMode`/`UsernsMode`, `ShmSize`, `CpuShares`/`CpuQuota`/`CpusetCpus`, `MemorySwap`, `NetworkMode` ∉ {"", default, bridge, satl}, `Runtime` ≠ `ocijail`. Rationale: half-honoured isolation options are a security trap. |
| 5 | `HostConfig.Mounts` (`--mount`) → 400 in M1; use `Binds`/`Tmpfs`. |
| 6 | Bind options: only `ro`/`rw`. SELinux `z`/`Z` and propagation modes → 400 (no SELinux, no shared subtrees on FreeBSD). |
| 7 | Ports: ranges (`8000-8010`) → 400; tcp/udp only (no sctp); every published port is host-mode, no ingress routing mesh in M1. |
| 8 | `RestartPolicy.unless-stopped` is accepted but behaves as `always` (no equivalent among SwarmKit restart conditions); the CLI rejects it outright. |
| 9 | `?platform=` must be `os/arch[/variant]`; the variant is ignored; a single component (`linux`) → 400 where Docker infers the rest. |
| 10 | `POST /containers/{id}/stop?t=<negative>` ("wait forever") degrades to the daemon's default stop timeout. |
| 11 | `DELETE /containers/{id}?link=1` → 400 (no container links). |
| 12 | `GET /containers/json`: `limit`, `size`, `filters` ignored; no `SizeRw`/`SizeRootFs`; **extra field `Platform`** (`os/arch`) per row, surfaced as the `PLATFORM` column in `satl ps`. |
| 13 | `GET /containers/{id}/json`: `Platform` is `os/arch` (Docker sends a bare OS string) plus SatL-only `JailID`; `Driver` always `zfs`; `GraphDriver`, `HostnamePath`, `LogPath`, `ResolvConfPath`, `AppArmorProfile` and size fields absent. |
| 14 | Logs are always multiplexed (`application/vnd.docker.multiplexed-stream`), even for `Tty:true` containers, SatL never allocates a TTY in M1. |
| 15 | `GET /images/json`: `all`/`filters`/`digests`/`shared-size` ignored; **extra field `Platform`**; `Containers` is a real count, `SharedSize` always 0, `Labels` always null, `ParentId` always empty. `Created` is the image config's `created` when the builder set one (pulled images usually carry it; `satl build` writes it at repack since M6f) and 0 for an image whose config has none, an old store entry simply predates the field being read. Since M9 there is one more thing to know: `repositories.json` is keyed by *reference*, so two tags of one image are **two rows sharing an `Id`**, where `GET /images/{name}/json` aggregates by image ID and lists both under `RepoTags` (#160). |
| 16 | `POST /images/create`: `fromSrc` (import) → 501; `X-Registry-Auth` accepted in base64url *or* standard base64. |
| 17 | Exec is non-interactive: `Tty:true` → 400 "tty not supported yet" (on create **and** start), `Privileged:true` → 400, `Detach:true` → 501, `DetachKeys` ignored; stdin on the hijacked socket is read and discarded. |
| 18 | `POST /exec/{id}/start` **without** `Connection: Upgrade`/`Upgrade: tcp` answers 200 + `application/vnd.docker.raw-stream` as a chunked body instead of hijacking (Docker hijacks in both cases). |
| 19 | Exec inspect: `ProcessConfig.privileged` always false, `DetachKeys` always empty, `CanRemove` always true. |
| 20 | Volumes: `local` driver only (ZFS datasets); other drivers → 400. `Scope` always `local`, `Status` always `{}`, no `UsageData`, filters ignored, `Warnings` always empty. |
| 21 | `GET /events`: `filters` is **not read at all**, not "accepted and ignored": no key is validated either, so a nonsense filter passes as silently as a real one. That is why `satl events --filter` is applied client-side and refuses an unsupported key itself (#161). `until` → 501; the legacy top-level `status`/`id`/`from` fields are omitted (only `Type`, `Action`, `Actor{ID,Attributes}`, `scope`, `time`, `timeNano`). |
| 22 | Answered as 404 `{"message":"page not found"}`: attach, commit, export, rename, restart, pause/unpause, update, top, stats, changes, archive, build (#144), and the `images/{name}/*` family other than the three verbs SatL serves, `history`, `get`, `load` and `push` (#152) stay 404. **`DELETE /images/{name}` (#155) and `GET /images/{name}/json` (#160) are implemented since M9**, so the family is dispatched method-first; a `DELETE` whose tail's last segment names a sub-verb still gets `page not found` (#158). **`POST /images/{name}/tag?repo=&tag=` is implemented** (audit N2): Docker's route, query params and 201; 404 on an unknown source, 400 on an unparseable target. A tag is one more reference to the same store entry, no blob is copied, both names keep resolving and both show in `GET /images/json`; tagging an image with the name it already has is a no-op success. |

## Container lifecycle semantics (M1 daemon)

These follow from the task model (a container **is** a one-shot Task, invariant #2) and
are the deviations most likely to surprise a Docker user.

| # | Deviation |
|---|---|
| 30 | **`start` on a stopped container is refused (409).** A Task is one-shot and immutable: re-running it would mean a new Task, i.e. a new container ID, which Docker's API cannot express. `docker start` therefore only works on a *created* (never-started) container. See the note below. |
| 31 | `kill` maps onto a graceful shutdown honouring the task's stop signal, grace period and then SIGKILL; `?signal=` is not forwarded. 409 when the container is not running. |
| 32 | `stop`'s `?t=` is ignored: the grace period lives in the task spec, which is immutable after creation. |
| 33 | `rm` deletes the backing Service as well, otherwise the orchestrator would immediately refill the slot with a new task. `?v=1` is a no-op (M1 has no anonymous volumes). |
| 34 | `ps`/`ps -a` show the newest task per slot. Retained task history (restart attempts) is not listed as extra containers. |
| 35 | Published ports are reachable from **other hosts**, not from the publishing host itself via `localhost`: pf applies `rdr` to packets entering an interface, never to locally generated traffic (Docker on Linux uses an iptables OUTPUT rule to make `localhost:port` work). Reach a local container by its own address, or from another machine. |
| 36 | Logs: `?since=` ignored, and `timestamps=1` stamps read time, the raw log files carry no per-line timestamps. |
| 37 | `/events`: `?since=` ignored (no replayable history); force-removing a *created* container emits `die` before `destroy`. |
| 38 | Exec: no TTY, stdin discarded, and output is delivered when the process exits rather than streamed live (streaming needs an fd-to-pipe dance that requires `unsafe`, which the workspace denies). Env is the task spec's plus the request's; the image's `ENV` is not re-read. User must be numeric. |
| 39 | Volumes: labels and driver options are accepted but not persisted; the driver must be `local`. |
| 40 | `HostConfig.AutoRemove` is accepted but not acted on server-side (the CLI performs the removal); a `PortBindings` entry with no host port is not allocated. Both produce a create-warning. |
| 41 | `ContainerSummary.ImageID` and image parent IDs are empty; the image ID is the manifest digest; `RestartCount` is always 0. |

**On #30**, the alternative is to make a container a *Service* rather than a Task, so
that `start` after `stop` creates a fresh task under a stable ID. That model is a better
fit for Docker's semantics and is worth revisiting when the rolling updater lands (M4),
since it also gives `docker update`-style flows somewhere to live. It is recorded here
as a deliberate, reversible M1 choice rather than an oversight.

## Swarm, nodes, services, tasks (M2)

| # | Deviation |
|---|---|
| 42 | `POST /swarm/init` is **idempotent**: SatL self-initializes a single-node cluster on first boot (architecture §1.2), so `init` re-initializes an existing one and `GET /swarm` already answers on a fresh daemon. `ForceNewCluster` → 501 (permanently -- #137); changing the advertise/listen address → 400 pointing at `satld.toml`; `AutoLockManagers` accepted since M7f (#151); `Spec`, `DataPathAddr`, `DataPathPort`, `DefaultAddrPool`, `SubnetSize` are accepted and ignored. |
| 43 | **`POST /swarm/join` accepts both tokens** (worker joins landed in M4; until then this entry read "manager tokens only"). The token decides the role, as in Docker. What a worker node then serves, and refuses, is #79-#86. |
| 44 | `POST /swarm/update` answers with the updated `Swarm` document (Docker returns an empty body, a superset clients discard) and applies exactly two updates: join-token rotation (the query flags) and, since M5, root CA rotation (`CAConfig.ForceRotate` above the stored counter, #97). Anything else → 501; `rotateManagerUnlockKey` rotates the autolock KEK since M7f (#151). `?version=` is accepted but not enforced. |
| 45 | `GET /swarm`: `TLSInfo` carries `TrustRoot` only; `DataPathPort` is 0 until the overlay lands (M3); `RootRotationInProgress` always false. |
| 46 | `GET /info`'s `Swarm` omits Docker's `Cluster` sub-document; `Nodes`/`Managers` are omitted when zero. |
| 47 | `GET /nodes` and `GET /services` reject a non-empty `?filters=` with 501 rather than silently listing everything. `GET /tasks?filters=` supports `id`, `name`, `service`, `node`, `desired-state`, `label`; any other key → 400. |
| 48 | Node **promotion and demotion apply live** (M4; until then promotion completed on restart): the role change reaches the node on its session, it renews its certificate to the new role and rebuilds its cluster runtime in place, a promotion joins Raft learner-first, a demotion goes through Raft first (SWK §12.3) and ends as a worker runtime. Running containers are not disturbed; the daemon does not restart. |
| 49 | `POST /services/create` accepts an empty `Spec.Name` and generates one, mirroring `POST /containers/create` without `?name=` (SwarmKit requires a name). |
| 50 | Service-spec fields rejected with 400 rather than silently dropped: `ContainerSpec.{Privileges, CapabilityAdd/Drop, Sysctls, Init, Isolation, Ulimits}`; `ContainerSpec.{Secrets, Configs}` (M5); `TaskTemplate.LogDriver`; `TaskTemplate.Runtime != container`; `Resources.Limits.Pids`; `Mounts.{Consistency, BindOptions, VolumeOptions, TmpfsOptions}` and mount types outside bind/volume/tmpfs; `EndpointSpec.Mode: "vip"`. `Mode.{ReplicatedJob, GlobalJob}` are **accepted since M7e** (run-to-completion services; `RestartCondition: none` on a job is still a 400, and `any` is rewritten to `on-failure`). `Placement.Preferences` is **accepted since M7d** for `Spread` only, with the descriptor validated (`node.id`, `node.hostname`, `node.labels.<key>`, `engine.labels.<key>`); any other strategy or descriptor is still a 400. |
| 51 | `Mode` with both `Replicated` and `Global` → 400; with neither → replicated 1. `UpdateConfig.Monitor == 0` means "use the SwarmKit default" (5 s), not "no monitor window". |
| 52 | `Endpoint.VirtualIPs` is always empty (DNS-RR only, no IPVS on FreeBSD, architecture §11.5). Task `Status.ContainerStatus.ContainerID` carries the jail name (= task ID). |
| 53 | Task documents omit `AssignedGenericResources`/`GenericResources`/`JobIteration`; node `Description.Engine.Plugins` is always empty and `Description.TLSInfo` is omitted. |
| 54 | `POST /services/{id}/update?rollback=` accepts only `previous`. `POST /nodes/{id}/update` and `/services/{id}/update` reject a missing or unparsable `?version=` with 400 before the backend is called. |
| 55 | Join token format `SATL-1-<digest>-<secret>` (SwarmKit's scheme, different prefix); the digest pins the CA bundle so a first contact over an untrusted channel cannot be MITM'd. Tooling that pattern-matches `SWMTKN` will not recognize it. |
| 56 | The internal protocol binds **two** ports: `2377` for the mTLS server and `2378` for the unauthenticated NodeCA bootstrap. Docker uses 2377 alone. `satl swarm join host:2377` derives the bootstrap port itself. |

## Networks (M3)

`GET|POST /networks`, `GET|DELETE /networks/{id}`, `POST /networks/{id}/(dis)connect`.
Two facts shape most of these: a network's addressing is allocated in Raft
(architecture §11.3), and an overlay has **one gateway per participating node**
rather than one cluster-wide (`docs/vxlan.md` §8).

| # | Deviation |
|---|---|
| 60 | **`Scope` follows the driver**, always: `overlay` → `swarm`, `bridge` → `local`. A create whose `Scope` contradicts its `Driver` is a 400, not a network with the other scope. |
| 61 | `IPAM.Config[0].Gateway` is **this node's** gateway on the network, never a cluster-wide one: the gateway is the containers' default route and the address their DNS responder binds to, so it must live on every participating node's own bridge, one shared address on one L2 segment is a duplicate address (`Network.node_gateways`, `docs/vxlan.md` §8). A node running no task on the network reports no `Gateway` at all, and `IPAM.Config` is `[]` when the network has neither a subnet nor a gateway here (a bridge network, or an overlay the allocator has not reached yet). Empty `Subnet`/`IPRange`/`Gateway` are omitted rather than sent as `""`. |
| 62 | **Extra field `Vni`**: the VXLAN network identifier the allocator assigned. Overlay networks only, absent on a bridge network and before allocation. |
| 63 | Create fields rejected with **400** rather than accepted and ignored: `EnableIPv6` and any IPv6 `Subnet`/`IPRange` (v1's IPAM and data plane are IPv4-only); `Internal` (every SatL network has egress through the node's pf NAT anchor); `Attachable` (every container is a task of a service, invariant #2); `ConfigOnly` and `ConfigFrom`; driver `Options` other than **`encrypted`**, the one driver option SatL reads, and only on the `overlay` driver: `{"encrypted": "true"}` (Docker's `--opt encrypted`) encrypts the VXLAN data plane between nodes with IPsec ESP/AES-128-GCM, `"false"` is accepted and means no encryption, and **any other value, including the empty string a raw API client sends for a bare option, is a 400** (`invalid driver option "encrypted"="": expected "true" or "false"`); the `satl` CLI normalizes a bare `--opt encrypted` to `encrypted=true` before the request leaves (#72), so both spellings work from the CLI; a truthy `encrypted` on a `bridge` network is a 400, and so is a truthy `encrypted` together with `Ingress: true`, ingress assignments go to every node, so an encrypted ingress network would ship its keyring cluster-wide instead of to participants only (there is no network-update route, so create is the only place the flag can be set); a driver outside bridge/overlay/local; `IPAM.Driver` other than `default`; `IPAM.Options`; more than one `IPAM.Config` entry (a SatL network has exactly one subnet); an `IPRange` or `Gateway` without a `Subnet`; and a **second `ingress` network**, a cluster has exactly one (SWK §9.5), checked at the API and again in the daemon under the store view, since the API's copy may be a stale follower's. |
| 64 | `local` is accepted as a synonym for the `bridge` driver: it is the *scope* SatL reports for it, and operators type it. |
| 65 | `CheckDuplicate` is accepted and ignored, SatL always enforces name uniqueness, and a duplicate name is a 409. Docker's newer `*bool` fields (`EnableIPv6`, `CheckDuplicate`, …) are accepted as `null`. |
| 66 | A network name must satisfy SatL's *service* naming rule (see #3), so dots are rejected. An **empty `Name` generates one** (`admiring_bostic`-style), mirroring `POST /containers/create` without `?name=`, where Docker requires a name. `Id` is the 25-char base36 object ID (see #1); inspect and remove accept an ID, an unambiguous ID prefix or the name, and an ambiguous prefix is a 409. |
| 67 | `Containers` is keyed by **task ID**, `EndpointID` is that same ID (SatL has no separate endpoint object), and `MacAddress` is **derived** from the address (`02:42:` + its four octets) rather than allocated, both ends of the overlay derive it, which makes the derivation a wire format (architecture §11.2). `IPv6Address` is always empty, and on a *bridge* network `IPv4Address`/`MacAddress` are empty too, those attachments are recorded without a cluster address (the node's own IPAM owns them, architecture §11.1). Terminal tasks are not listed: retained restart history would otherwise make one replica look like five (see #34). |
| 68 | `GET /networks?filters=` → 501 rather than silently listing everything (as for nodes and services, #47). Docker's predefined `bridge`, `host` and `none` networks **do not exist**: the list holds store objects only, and the node's own bridge (`network_name` in `satld.toml`, default `satl0`) is not one. `NetworkMode` on container create still accepts `bridge`/`default`/`satl` (#4). |
| 69 | `POST /networks/{id}/connect` and `/disconnect` → **501**. A task's attachments are allocated once, at creation (architecture §5 step 3), and its spec is immutable: hot-plugging a network onto a running container means replacing the task, i.e. a different container ID than the client named, the same wall as #30. The supported path is to declare the network at service creation, or to update the owning service's networks, its tasks are then replaced with the new attachments, under new container IDs. The network and the container are resolved first, so a typo is still a 404. At the API layer only `EndpointConfig.Aliases` would be honoured: `IPAMConfig` (the cluster allocator owns addresses), `Links` and `DriverOpts` are 400. |
| 70 | `DELETE /networks/{id}` is a **409** while anything still uses the network: a non-terminal task attached to it *or naming it in its spec* (Docker's "has active endpoints"), or a service whose task template references it, its next task could not be placed, and SwarmKit refuses the same way. Deleting under a live task would black-hole it *and* let the allocator hand its subnet out again. Terminal tasks do not block removal, where Docker counts a stopped container's endpoint. |
| 71 | Two creates are honoured in part and answer with a `Warning` instead of failing: a **`bridge`-driver network** is recorded and can be referenced, but M3 programs one bridge per node and tasks attach to that, not to a bridge of their own; and an overlay's requested `IPAM.Config[0].Gateway` is **reserved and handed to nobody**, the real gateways are per node (#61), so the only meaning left for the request is "keep this address out of the pool". |

## Service discovery (M3)

There is no VIP: a service name resolves to its running tasks' addresses, shuffled per
query (architecture §11.5, #52). What follows is about *which* names a given container
can resolve, and in what order, established against Docker's own source, not its docs,
because the docs do not state it. Verified in moby `master` @ `ec13aca` (the code is
identical in the shipped `v28.5.2`; libnetwork has moved from `libnetwork/` to
`daemon/libnetwork/`), and none of it is covered by a Docker test, so treat Docker's
*order* as emergent behaviour rather than as a contract.

| # | Deviation |
|---|---|
| 73 | **Resolution is scoped to the querying task's networks, searched in attachment order.** Same as Docker on the two things that matter: a container attached to several networks resolves names on **all** of them (`Sandbox.resolveName`, `daemon/libnetwork/sandbox.go`, iterates every endpoint of the sandbox), and a name present on two of them is answered from **one** network, the first that holds it, whole, never a merge of both (the loop `return`s on the first `nw.ResolveName` hit; merging would round-robin one client's traffic across two different services). A network that holds the name but no record of the queried type answers `NOERROR` with no records and the search stops there, exactly as Docker's `DNSBackend` contract requires. The **order** deviates: SatL walks `TaskTemplate.Networks` in the order the spec declares them, where Docker sorts endpoints by default-gateway preference (`Endpoint.Less`: `--gw-priority`, then non-`docker_gwbridge`, then non-internal, then how many gateways the endpoint has, and only then network name ascending), re-sorted in swarm mode to put overlay networks before ingress before local (`ByNetworkType`) with a non-stable `sort.Sort`. SatL takes the spec's order because it is the operator's own declaration and is identical on every node and for every query; Docker's is undocumented and formally unspecified between equal endpoints. Consequence to know: **two services of the same name on two of a task's networks resolve to whichever the service spec lists first**, and the answer never mixes them. |
| 74 | Three narrower differences in the same responder. (a) A query whose **source address is not one of the node's own tasks** is forwarded upstream and never answered from the table, where Docker's resolver is reachable only from inside the container's own network namespace and so never faces the question. An overlay network's per-node gateway addresses all sit on one L2 segment, so every task of that network on *every* node can reach *every* node's responder; a task's `resolv.conf` points at its own node's gateway (#61), so only a container that hardcodes another node's address is affected. (b) The **`<name>.<network>` qualified form is not implemented** (Docker's `ResolveName` splits `a.b.c.d` into every "name in network" reading); an unqualified name is the only form, so a service must be named uniquely across a task's networks to be addressable unambiguously. (c) With **no upstream resolver configured**, a name in none of the scope's networks is `NXDOMAIN`, where Docker answers `SERVFAIL` when it can reach no upstream, SatL is then the container's only resolver, so the name genuinely does not resolve. With upstreams configured both forward and relay the upstream's answer verbatim, `NXDOMAIN` included. |

## Published ports (M3)

`EndpointSpec.Ports[].PublishMode` is where SatL and Docker differ most visibly,
and the difference is a data-plane one: Docker's `ingress` is a *routing mesh*,
SatL's is a redirect on the nodes that run the service. Docker's behaviour was
read rather than remembered, the mesh from Docker's own documentation ("The
routing mesh enables each node in the swarm to accept connections on published
ports for any service running in the swarm, even if there's no task running on
the node", *Use swarm mode routing mesh*), the validation rules from SwarmKit's
source (`manager/controlapi/service.go`, `validateEndpointSpec`), and the
allocation model from the behavioural spec (SWK §3.7, §9.5).

| # | Deviation |
|---|---|
| 75 | **`PublishMode: ingress` is a full routing mesh on managers** (M6d; it was "ingress-lite" until then). The port is allocated centrally, exactly as SwarmKit does it, one cluster-wide owner per `(protocol, published port)`, sticky across updates, auto-assigned from 30000–32767 when the request says `0`. Every **manager** then answers on the port: a node running a replica redirects to it, a node running none relays over the `ingress` overlay network to a healthy task's ingress address, with a return-path SNAT from the relaying node's ingress gateway (`docs/networking.md`, M6d). Two consequences a Docker user will notice. **The client address is lost on relayed connections**, the task sees the relaying node's gateway, exactly as behind Docker's mesh (IPVS SNATs the same way); where the real address matters, M6e's opt-in PROXY-protocol mode preserves it. And **a worker keeps the pre-mesh behavior**: with no store replica it cannot compute the cluster-wide pool, so on a worker only a local replica is answered, on an all-manager cluster (the supported shape in v1) the mesh covers every node. Health-checked membership is the M6c table-backed pool: an unhealthy task is out of every node's table within the measured ~10 s bound. The first ingress publisher lazily creates the `ingress` network (SWK §9.3); a cluster that never publishes ingress ports never grows one. |
| 76 | **Several tasks of one service on one node share one redirect, round-robin.** Two replicas the scheduler placed together, or, from M4, the old and the new task of a slot during an update, publish the same port on the same node. SatL emits **one** pf rule with an address pool (`-> { 10.88.0.2, 10.88.0.3 } port 80 round-robin`), so connections alternate between that node's own tasks. Docker balances over the whole cluster instead (IPVS over the service VIP), so the same `-p 8080:80` spreads over every replica in Docker and over this node's replicas here. Note what is *not* done: emitting one rule per task would be silently wrong, pf evaluates translation rules in order and the **first** match decides (pf.conf(5)), so every task but one would look published and never receive a connection. |
| 77 | **DNS-RR and ingress ports coexist**, where SwarmKit rejects the combination outright ("EndpointSpec: port published with ingress mode can't be used with dnsrr mode"). Its reason does not apply here: the rejection exists because the mesh load-balances on a VIP and DNS-RR has none. SatL has no VIP at all (#52), and its ingress-lite redirect needs none, the target is a task address on the node doing the redirecting. Since every SatL service is DNS-RR (`vip` is a 400, #50), rejecting the pair would mean rejecting published ports entirely. |
| 78 | **An ingress-published container shows no port in `ps`/`inspect`, on a node that is redirecting one.** `Task.Status.PortStatus`, which feeds `GET /containers/json`'s `Ports` and `docker ps`'s `PORTS` column, carries host-mode bindings only, exactly as SwarmKit's executor reports them (`swarmd/dockerexec/controller.go`, `parsePortStatus`, which stamps every entry `PublishMode: HOST`). The *values* therefore match Docker; what differs is what an empty column means. In Docker it means the container has no host binding and the port lives in the ingress namespace; here it means the container has no host binding and there is, additionally, a live `rdr` on this very node sending that port to it. Read the service (`satl service ls`'s `PORTS`, `Endpoint.Ports`) for ingress publishing, or `pfctl -a satl/rdr -s nat` for what a node actually redirects. |

## Worker nodes (M4)

A worker holds no replicated store (architecture §1.2), so its REST surface splits in
two: cluster-scoped endpoints answer Docker's own refusal, local operations are served
from the node's local task records. The refusal was established from moby's source,
not from memory: the message is `errNoManager`'s active-worker arm
(`daemon/cluster/cluster.go`, "This node is not a swarm manager. Worker nodes can't
be used to view or modify cluster state. Please run this command on a manager node or
promote the current node to a manager."), the type is a `notAvailableError`
(`daemon/cluster/errors.go`), and `api/server/httpstatus` maps that to **503 Service
Unavailable** with the usual `{"message": ...}` body.

| # | Deviation |
|---|---|
| 79 | **Cluster-scoped endpoints on a worker answer 503 with the exact Docker message above**: `/swarm` (inspect/update/join-token rotation), `/nodes`, `/services`, `/tasks`, and, a deviation within the deviation, **all of `/networks`**: a SatL network is a store object even when its driver is `bridge` (#68: the predefined local networks do not exist), so a worker has no network list to serve where a Docker worker still lists its local networks. |
| 80 | **Container lifecycle mutations are refused on a worker with the same 503**: create/start/stop/kill/rm (and therefore `satl run`). Docker allows these, a Docker worker still runs standalone containers, but SatL has no standalone containers: every container is a Task of a Service (invariant #2), and a task mutation is a store write a worker cannot propose (invariant #1). Run these on a manager; the scheduler places the task. |
| 81 | **Container reads are served on a worker from its local task records** (the persisted assignments, architecture §7.2): `ps`/`ps -a` (this node's tasks only, same view a Docker worker gives), `inspect`, `logs`, `wait` (a local poll, not a store watch), and `exec` (create/start/inspect). Volumes and images (list/pull) are node-local and unchanged. |
| 82 | `GET /events` on a worker carries **local events only** (image pulls). Task state transitions are store writes and are emitted on managers; a Docker worker would emit its local container events. |
| 83 | `GET /info` on a worker: `Swarm.ControlAvailable: false`, `LocalNodeState: active`, `RemoteManagers` from the session's manager list, `Nodes`/`Managers` omitted (zero, Docker fills them only on managers). Container counts are the worker's own. |
| 84 | `POST /swarm/init` on a worker → 503 "This node is already part of a swarm. Use \"docker swarm leave\" to leave this swarm and try again." (Docker's `errSwarmExists`, verbatim). On a manager, init stays the idempotent success of #42. |
| 85 | `POST /swarm/join` on a node already in a swarm: Docker always refuses; SatL keeps the M2 clean-state rule, a manager may re-join if its store holds nothing but itself (#42's self-init makes every fresh node a cluster), and a worker may re-join if it runs no tasks. A worker running tasks is a 409 naming them. |
| 86 | `POST /swarm/leave` on a worker needs no `force` (matches Docker). Its containers' tasks are rescheduled by the managers once the node expires from the dispatcher (TTL → Down → eviction); locally, the fresh single-node runtime's first assignment snapshot is empty, so the agent's init pass stops and releases the old cluster's containers (architecture §7.2). |

The worker's DNS responder answers exactly like a manager's: both tables are built
from the assignment stream and the local task DB (architecture §11.5), so #73/#74
apply unchanged on every node role.

## Healthchecks (M4)

`ContainerSpec.Healthcheck`, the **service** spec's, `POST /services/create`, is
honoured: the probe runs as `ocijail exec` inside the task's jail with the container's own
env, cwd and user, and the semantics are Docker's, taken from moby's `daemon/health.go`
rather than from the docs, defaults `interval` 30 s, `timeout` 30 s, `retries` 3,
`start_period` 0, except on a service that publishes a port, where they are tightened
(#125, #126). A **container**'s `Config.Healthcheck` is *not* read (#127), so `satl run`
publishes without a probe. The rest, unchanged: the
first probe one interval *after* the container starts, never at t=0; exit 0 healthy and
anything else a failure; `retries` **consecutive** failures needed for `unhealthy`, with
a single success resetting the streak; failures ignored while the status is `starting`
*and* the probe began inside `start_period`; `State.Health.Log` bounded to 5 results and
each `Output` to 4096 bytes; a probe that cannot be run, or that outlives its timeout,
recorded as exit code `-1` with Docker's own wording (`Health check exceeded timeout
(2s)`). `CMD` execs the argv, `CMD-SHELL` goes through `/bin/sh -c`, `NONE` and an
unrecognized `Test[0]` mean no probe (a warning, exactly as Docker).

What differs is what health *does*, because a container here is a Task.

| # | Deviation |
|---|---|
| 87 | **Health gates the task state machine**: a task with a healthcheck is not reported `RUNNING` until a probe has passed, it stays `STARTING`, which renders as Docker's `running` state (#2) with `Status` "Up 2 seconds (health: starting)". The consequence is deliberate and is the reason the feature exists: the DNS responder only answers with `RUNNING` tasks (#73) and a rolling update only promotes on observed `RUNNING`, so neither can send traffic to a container that has not passed a probe. Docker has no equivalent, its container is `running` the moment it starts, whatever its health. |
| 88 | **An unhealthy task is stopped and `FAILED`; Docker leaves an unhealthy container running.** `retries` consecutive failures outside the start period end the task: it is stopped with its own stop signal and grace period, reported `FAILED` with the streak and the last probe's exit code in `Status.Err`, and the orchestrator's restart supervisor replaces it under the service's restart policy. This is SwarmKit's behaviour, not an invention (`ErrContainerUnhealthy`, SWK §15.2, both at start time and while running); Docker's own `--restart` never reacts to health at all. A task that never becomes healthy therefore *fails* rather than staying `starting` forever, `start_period` is the only grace. |
| 89 | **`State.Health` is node-local**: it appears only when the node answering the request is the one running the task. A worker reports health for its own tasks; a manager reports it for tasks placed on itself and **omits it for every task placed elsewhere**, where Docker (single-host) always has it. Health never enters the Raft store, a worker holds only ephemeral executor state (invariant #1), so `Task` documents (`GET /tasks`, `satl service ps`) carry no health either, matching `docker service ps`, which shows none. It is also not persisted: after a `satld` restart an adopted running task starts again at `starting` and is re-probed. |
| 90 | **`Healthcheck.StartInterval` is not supported** (the service spec has no such field). During the start period, while the container has never been healthy, SatL probes on `min(interval, 5 s)`, Docker's default `start_interval`, so a slow starter is not held back by a long `interval`, and an interval shorter than 5 s is never slowed down. Supporting the field means adding it to `satl-core`'s `HealthConfig`. |
| 91 | **The image's `HEALTHCHECK` is not inherited.** Only the healthcheck in the service/container spec is honoured; an image that declares one gets no probe and its task reaches `RUNNING` on start, where Docker (and Docker Swarm) would inherit and gate on it. `Test: [""]`, Docker's "inherit from the image" marker, therefore means "no healthcheck" here. Inheriting needs the image config's healthcheck plumbed through `satl-image` into the task spec at service-create time. |

## Rolling updates (M4)

`Service.UpdateStatus` and `Service.PreviousSpec` are written by the rolling updater
(`satl-orchestrator::update`, architecture §5), and read back through
`GET /services/{id}` and `satl service inspect`. The states and their transitions are
SwarmKit's; what differs is when they move and who may clear them. Docker's behaviour
here was taken from SwarmKit's source and spec (`orchestrator/update/updater.go`,
SWK §7.3) rather than from the Docker documentation, which does not describe it.

| # | Deviation |
|---|---|
| 92 | **A paused update is resumed by the next `POST /services/{id}/update`** (until this landed, the entry read "is *not* resumed", and a paused service had to be removed and recreated). The control backend now writes `UpdateStatus` on every update, both arms taken from SwarmKit's own control API (`manager/controlapi/service.go`, `UpdateService`) rather than from the Docker documentation, which does not describe the field: a normal update **clears** it, so the next rollout starts clean and a `paused`/`rollback_paused` service is unstuck by pushing a corrected spec; `?rollback=previous` sets it to `rollback_started` with SwarmKit's own message, `manually requested rollback`, so the updater knows a rollout is under way and applies `RollbackConfig` rather than `UpdateConfig`. Clearing happens on **every** update, not only one that really changes the spec, as in SwarmKit, and for a reason worth knowing: whether the spec changed is decided by the store when the transaction commits, so an update posting an identical spec clears the status and replaces no task (nothing becomes dirty). The tasks of a paused service were always still reconciled, scale, restart and node eviction keep working, and still are; what changes is that further slots are replaced again. |
| 93 | **An update takes at least `Monitor` per batch.** SwarmKit starts the next batch as soon as the previous task reaches `RUNNING` and keeps watching for failures in the background; SatL makes the failure-observation window part of the batch, so with the default `Parallelism: 1` and `Monitor: 5s` a six-replica update takes at least 30 s. That is what makes the batch health-gated (#87): a task that fails inside its window is caught before the next slot is disturbed. Set `Monitor` to a small value to get SwarmKit's pace back; `MaxFailureRatio` still behaves as documented. |
| 94 | **`UpdateStatus.Message` is SatL's own wording** (`updating: 3 of 6 slots updated`, `update paused: 2 of 6 tasks failed`, `rolling back: ...`). Docker's strings ("update paused due to failure or early termination of task ...") name a task; these name the counts, which is what an operator watching a six-replica rollout needs. Both are free text in the API and neither is a contract. `StartedAt` survives the transition into a final state and into a rollback, so it always means "when this rollout began". |
| 95 | **`PreviousSpec` is cleared by an automatic rollback**, exactly as SwarmKit clears it: after a `rollback_started`, `Service.PreviousSpec` is `null` rather than the spec that failed. A `POST /services/{id}/update?rollback=1` therefore has nothing to roll back to until the next update, which is deliberate, the spec that just failed is not a target to return to. Docker behaves the same way; it is documented here because the field's absence looks like data loss otherwise. |

## CLI (M4)

| # | Deviation |
|---|---|
| 96 | `satl service create`/`update` carry Docker's twelve policy flags with Docker's names, value spellings and defaults, `--update-parallelism`, `--update-delay`, `--update-failure-action`, `--update-monitor`, `--update-max-failure-ratio`, `--update-order` and the six `--rollback-*` counterparts (parallelism 1, delay 0, failure action `pause`, monitor 5 s, ratio 0, order `stop-first`; `--rollback-failure-action` takes `pause`/`continue` only, as docker's own help documents, although the daemon would accept `rollback`). **A flag left out keeps the value the service already has**: `update` reads the stored spec, changes only what the flags name and posts the whole document back, so `satl service update --image` cannot silently reset a rollback policy (it did, until this landed, every field of `UpdateConfig` except `Parallelism` and `Delay` was absent from the CLI's own copy of the document and therefore erased on every update, which is why the M4 DoD scenario had to reach for `curl --unix-socket`). Two Docker flags are still missing: `--rollback` (a manual rollback needs `POST /services/{id}/update?rollback=previous`) and `--force` (a restart with no spec change needs `TaskTemplate.ForceUpdate` bumped through the API). |

## Secrets and configs (M5)

`POST /secrets/create`, `GET /secrets`, `GET /secrets/{id}`, `DELETE /secrets/{id}` and
their four `/configs` counterparts are Docker's, with Docker's shapes: a create takes a
`SecretSpec`/`ConfigSpec` whose `Data` is base64 (standard or URL-safe, padded or not,
#16's rule) and answers `201` with `{"ID": "..."}`; a read answers the `Secret`/`Config`
document with `Version`, `CreatedAt`, `UpdatedAt` and `Spec`; a delete answers `204`.
Size limits are SwarmKit's (500 KiB for a secret, 1000 KiB for a config) and the
refusal names the limit in bytes. `ContainerSpec.Secrets`/`Configs` carry Docker's
`SecretID`/`SecretName`/`File{Name,UID,GID,Mode}` shape, `Mode` being a Go `os.FileMode`,
**decimal** on the wire, so the default `0444` is `292`. References are resolved by
**ID**, as SwarmKit resolves them: the client turns a name into an ID first (`satl` and
the Docker CLI both list the objects to do it), and a reference naming an object that no
longer exists is refused at service-create time rather than failing every task later.

| # | Deviation |
|---|---|
| 97 | **`POST /secrets/{id}/update` and `POST /configs/{id}/update` answer 501**, with the rotation recipe in the message ("secrets are immutable; rotate by creating a new secret, updating the services that use it, and removing the old one"). Docker's endpoint accepts a whole spec but honours only a change of `Labels`, the payload is immutable there too, and a 200 that silently ignored the `Data` an operator just sent is the worst of the three possible answers. Rotation is the documented path and it is the one that actually restarts the tasks that hold the old payload. |
| 98 | **Deleting a secret/config that anything still references is a 409** naming the services to fix first ("secret db_password is in use by the following service(s): web, api. Update or remove them first"; at most four names, then "and N more"). Docker answers 400 here, through SwarmKit's `InvalidArgument`; SatL follows its own network precedent (#70) instead, because "the object exists but is in the wrong state" is what 409 means and it is what the CLI turns into a usable exit. "In use" is wider than Docker's check in one way that matters: it includes every service whose task template merely *references* the object, whose next task would be unpreparable, as well as every non-terminal task holding it. A terminal task is history, not a use. |
| 99 | **`GET /secrets?filters=` and `GET /configs?filters=` answer 501** for any non-empty filter, rather than ignoring it and listing everything (precedent #47). `satl secret ls`/`config ls` therefore list unfiltered; filter with the client. |
| 100 | **A secret's `File.Name` must be a relative path**, and is materialized under `/run/secrets/<name>` on the node. An absolute target is a 400 ("secret target must be a relative path; secrets are mounted under /run/secrets"). Docker allows an arbitrary absolute path and bind-mounts the file there; SatL delivers secrets through one per-task tmpfs (invariant #7), and a secret written anywhere else would be a secret on disk. A config target may be absolute (that is how a config lands in `/etc`) or relative, in which case it is rooted at `/`, exactly as Docker's is. Neither may contain a `..` component (400). `File.Mode` above `0o7777` is a 400, Go's `os.FileMode` has type bits above the permission bits and SatL will not silently mask them. |
| 101 | **`/run/secrets` is not remounted read-only.** Docker mounts its secret tmpfs `ro`; SatL's is a writable tmpfs whose files carry the requested mode (`0444` by default) and ownership, so an unprivileged process in the jail cannot alter them but root inside the jail can. The protection is the file mode, not the mount flag. Making the mount read-only needs a second mount pass after the files are written, which is deferred. |
| 102 | **`File.UID`/`File.GID` must be numeric.** Docker resolves user and group *names* from the image's `/etc/passwd` and `/etc/group`; SatL does not read the image's user database, so a name is refused when the task is planned, the task is `REJECTED` with a message naming the reference, not silently owned by root. The API accepts the string as sent (it is Docker's own type) and defaults an omitted value to `"0"`. |
| 103 | **`SecretSpec.Driver` is a 400** ("secret drivers are not supported"): there are no driver plugins, so an external secret store cannot be honoured and a secret quietly stored in the cluster instead would be exactly the leak the driver existed to prevent. **`Templating` is a 400 for both secrets and configs** when its `Name` is non-empty, SatL has no template engine, and a config whose `{{ }}` placeholders were never expanded is a broken file delivered as a correct one. A `null` or `{}` member is what a Go client marshals for an unset struct and means unset, not "no driver". |

## Root CA rotation (M5)

`docker swarm ca --rotate` maps onto `satl ca rotate` (and `satl ca --rotate`); the
wire surface is Docker's own, `POST /swarm/update` with `Spec.CAConfig.ForceRotate`
above the stored counter, progress read from `GET /swarm`'s
`RootRotationInProgress` and `TLSInfo.TrustRoot`. Mechanics in architecture §12.3.

| # | Deviation |
|---|---|
| 104 | **Only `ForceRotate` starts a rotation; a caller-supplied signing cert/key is refused as an unsupported spec update** (501, from #44's rule). Docker also accepts `SigningCACert`/`SigningCAKey` in `CAConfig` (rotate *to* given material) and external CAs; SatL always mints the new root itself. `TLSInfo.CertIssuerSubject`/`CertIssuerPublicKey` (DER blobs) stay empty, `TrustRoot` is filled and is what `satl ca` prints. |
| 105 | **A rotation cannot be started while one is in progress** (409, with the operator's way out in the message: wait, or `satl node rm --force` a node that will never converge). SwarmKit instead *replaces* the running rotation with a new one; SatL refuses because the replacement path multiplies the trust-bundle states every node must traverse and the recovery story ("which tokens are valid now?") stops being answerable from one `GET /swarm`. Revisit if a real cluster ever needs to abandon a rotation whose new key was itself compromised mid-flight. |
| 106 | **Join tokens rotate twice per CA rotation, at start and at completion**, because a SatL token digest pins the *whole* trust bundle (#43-adjacent; SWK §16.2) and the bundle changes at both moments (old → old+new → new). Docker regenerates tokens only at completion, since its `GetRootCACertificate`/token digest keeps serving the old root alone during the rotation. Consequence for tooling: a token read before `satl ca rotate` is void the moment the rotation starts, not when it finishes; re-read it after (`satl swarm join-token`). A stale token fails the join with the bundle-digest error naming the rotation. |

## Compose (M5)

`satl compose up|down|ps|config` reads a Compose Spec file. The command name is
docker's; the semantics are `docker stack deploy`'s, and the naming conventions
were read out of docker's own source rather than remembered, compose-go's
`withNamePrecedenceLoad`, `NormalizeProjectName` and `DefaultFileNames`, docker
compose's `pkg/api/labels.go`, and docker/cli's `cli/compose/convert`
(`Namespace.Scope`, `convertServiceNetworks`).

| # | Deviation |
|---|---|
| 110 | **`satl compose up` creates services, not containers.** Docker has two worlds, `docker compose` makes containers on one host, `docker stack deploy` makes services on a swarm. SatL has no standalone containers (invariant #2, #1) and the cluster is always on (#42), so a compose file necessarily deploys **one service per compose service**, on a shared overlay, scheduled across the cluster. Everything that follows from that: a service is named `<project>_<service>` and a network `<project>_<key>` (docker stack's `Namespace.Scope`, underscore, note compose v2 names *containers* with a hyphen); `deploy:` is honoured rather than ignored; `container_name:`, `scale:` and the whole single-host half of the spec are refused; the number of containers is `deploy.replicas`, not one. The deviation is stated in `satl compose --help` as well as here, because a familiar command that does something else owes the operator a warning. |
| 111 | **Every service attachment carries the compose service name as a DNS alias.** `<project>_redis` would not answer to `redis`, which is the hostname the compose file itself uses, so each attachment gets `Aliases: ["<service>"]`, exactly what `docker stack deploy` does (`convertServiceNetworks` appends `service.Name` for user-defined networks), and SatL's DNS responder resolves an alias like a service name (`satl-overlay::endpoints`). Per-network `aliases:` are appended after it. Consequence: two stacks that share one **external** network cannot both declare a service of the same name, the alias would be ambiguous, and DNS-RR would answer with tasks of both (#73). Give each project its own network (the default) or rename the service. |
| 112 | **The default network is an overlay, and `driver: bridge` is refused.** `docker compose` creates a *bridge* network per project; a stack that spans the cluster needs the overlay driver (#60), so `<project>_default` is created with `-d overlay` and a compose network declaring any other driver is refused rather than silently made node-local. `satl network create -d bridge` still exists for a node-local object. A service that names no `networks:` joins `default`, and a declared network no service attaches to is not created (a warning says so), both compose's own rules. |
| 113 | **Anything outside the supported subset is refused with the file, the service and the key named.** The subset is `services`, `networks`, `volumes`, `secrets`, `configs` and, per service: `image`, `command`, `entrypoint`, `environment`, `env_file`, `ports`, `volumes`, `secrets`, `configs`, `healthcheck`, `labels`, `user`, `working_dir`, `hostname`, `stop_signal`, `stop_grace_period`, `restart`, `networks`, `depends_on`, and `deploy.{mode,replicas,labels,resources,placement,restart_policy,endpoint_mode,update_config,rollback_config}`. Refused with a reason each: `build`, `privileged`, `cap_add`/`cap_drop`, `devices`, `network_mode`, `profiles`, `extends`, `container_name`, `scale`, `cpus`/`cpu_shares`/`cpu_quota`/`cpuset`, `mem_limit`/`mem_reservation`/`memswap_limit`, `pids_limit`, `sysctls`, `ulimits`, `init`, `pid`, `ipc`, `uts`, `userns_mode`, `security_opt`, `shm_size`, `tmpfs`, `links`/`external_links`, `volumes_from`, `expose`, `dns`/`dns_search`, `extra_hosts`, `logging`, `platform`, `read_only`, `tty`, `stdin_open`, `stop_timeout`, `develop`, `pull_policy`, `runtime`, `cgroup`/`cgroup_parent`/`device_cgroup_rules`, `deploy.preferences`, `deploy.resources.*.pids`/`devices`/`generic_resources`, and top-level `include`. A key with no bespoke reason still fails, with the list of keys that *are* read. Only `x-` extension keys are accepted and ignored, the Compose Spec reserves them, and a YAML anchor block usually lives in one. Docker's own stack deploy prints `Ignoring unsupported options: …` and carries on; a 200-line file that half-deployed is the trap this project refuses. |
| 114 | **No variable interpolation.** `${TAG}` and `$TAG` are refused, naming the line and column, because passing them through literally would deploy a service asking for the tag `${TAG}` and there is no `.env` loading, no `${VAR:-default}` grammar and no `--env-file` for the file itself. Compose's escape **is** applied: `$$` becomes a literal `$`, in one text-level pass, so a command written for compose (`sh -c 'echo $$HOME'`) means the same thing here. Substitute the values before deploying (a generated compose file, or `satl service update`). |
| 115 | **One `-f/--file`, and no merging.** No override file, no `include:`, no `extends:`: docker's merge rules are intricate and a half-merge is worse than none. Discovery is docker's: `compose.yaml`, `compose.yml`, `docker-compose.yml`, `docker-compose.yaml` in that order, walking up from the working directory, first directory with a candidate wins, several candidates in one directory is a warning naming the winner. |
| 116 | **Project name**: `-p`, then `COMPOSE_PROJECT_NAME`, then the file's `name:`, then the project directory's base name, compose's own precedence. Normalization is compose-go's `NormalizeProjectName`: lowercase, then **delete** (not replace) every character outside `[a-z0-9_-]`, then trim leading `_`/`-`; so a directory called `my.app` is project `myapp`. A name given explicitly must already be normalized, and is refused with compose's own message otherwise. |
| 117 | **`down` removes exactly what `up` created, scoped by label.** Every service and network `up` creates carries `com.docker.compose.project=<project>` (plus `com.docker.compose.service` / `com.docker.compose.network` for the compose key), and `down` acts on that label and nothing else, an object with the name this project would use but without its label belongs to somebody else, and both `up` and `down` refuse to touch it. `down` therefore needs no compose file at all: `satl compose down -p <project>` is enough, as it is in docker (`Down()` takes a project *name*). An orphan, a service still carrying the label that the file no longer declares, is *warned about* by `up` and removed with `--remove-orphans` (docker's rule), and removed unconditionally by `down`, which works from the label rather than from the file. Docker also requires the `com.docker.compose.config-hash` label to exist before it will remove a container; SatL does not compute a config hash (it reposts the whole spec and lets the store decide what changed, #92). |
| 118 | **`down` waits for the tasks before removing a network, and refuses `-v`.** Deleting a network under a live task is a 409 (#70) and the tasks of the services just removed take their stop grace period to become terminal, so the network delete is retried against the daemon's own answer for up to 90 s (a warning says it is waiting). `-v/--volumes` is **refused**: a volume is a node-local ZFS dataset, one per node that ran a task, and volume labels are not persisted (#39), so there is no label to scope a removal by and no single node to remove it from. The message points at running `satl volume ls` + `satl volume rm` on each node that ran a task -- the CLI speaks to a unix socket only, so there is no remote `--host` to aim at either -- and `satl compose config` prints the names. |
| 119 | **Volumes are declarations only.** Nothing is created for a top-level `volumes:` entry: a named volume is a dataset the agent makes on the node where a task first uses it. The name is namespaced (`<project>_<key>`) unless `name:` or `external: true` says otherwise, `driver:` must be `local` (#20) and `driver_opts:` is refused. A service mounting one gets a warning that the data is per node and does not follow a rescheduled task. A **bind** mount must be an absolute path, a relative one is refused, because it is a path on the client's filesystem and not the nodes', and gets a warning that it must exist on every node the scheduler may choose (a task whose bind source is missing is rejected). |
| 120 | **Secrets and configs must already exist: only `external: true` is accepted.** `file:` is refused with the recipe (`satl secret create <name> <file>`, then `external: true`), because a secret is immutable (#97): a second `up` after editing the file would silently keep the old payload, and `down` would then have to decide whether to delete cluster secret material. `environment:` is refused too (the payload would pass through `satl`'s own process environment). `name:` names the stored object when it differs from the compose key; the per-service `target:` defaults to the compose key, and a secret's target is relative, under `/run/secrets` (#100). References are resolved to store IDs with one `GET /secrets` / `GET /configs` before anything is posted, so a missing one fails before any service is created (#109). |
| 121 | **A file `mode:` is read as octal however it is written.** This is a place where two YAML versions disagree silently: an unquoted `0440` reaches a YAML 1.2 parser as the decimal digits `440` (there is no octal-by-leading-zero), while docker's go-yaml resolves it as octal 0o440. SatL reads the digits as **octal** in both spellings, so `0440`, `"0440"` and `440` all mean `0o440`, the mode the operator wrote. The cost is that a bare `mode: 700` is `0o700` here and decimal 700 (`0o1274`) in docker; the benefit is that nobody gets a wider mode than they typed. A digit outside 0-7 is refused. |
| 122 | **`depends_on` is a warning, not an order.** There is no startup ordering in a cluster scheduler: the orchestrator places every task as soon as it can. The short form (and `condition: service_started`, which means the same thing) is accepted with a warning naming the services, and an undefined service name is an error. `condition: service_healthy` and `service_completed_successfully` are **refused**, because an application that asks for them relies on them: retry the dependency in the container and give it a `healthcheck:`, which is what actually gates traffic here (#87). Docker's own `stack deploy` drops `depends_on` **silently**, it is in neither its unsupported nor its deprecated list, so nothing is printed at all. |
| 123 | **Both `restart:` and `deploy.restart_policy:` are honoured**, the deploy policy winning and saying so; `docker stack deploy` lists `restart` in its `UnsupportedProperties` and drops it. `restart: no|always|on-failure[:N]` maps onto the swarm conditions `none|any|on-failure` (+ `MaxAttempts`); `unless-stopped` is refused (#8, #26). Also mapped rather than dropped: `labels:` become the **container**'s labels and `deploy.labels:` the **service**'s (docker's own split); `deploy.endpoint_mode` accepts `dnsrr` only (#50); `deploy.mode: global` becomes a global service; `deploy.placement.max_replicas_per_node` becomes `Placement.MaxReplicas`; `healthcheck.disable: true` becomes `Test: ["NONE"]`, a bare string becomes `CMD-SHELL`, and a list not starting with `CMD`/`CMD-SHELL`/`NONE` is refused rather than silently producing no probe (#91); `healthcheck.start_interval` is refused (#90). A duplicate environment name keeps its first position and takes the later value, because compose merges into a map and a duplicate on the wire would leave the winner to whoever reads the list. |
| 124 | **`up` is always detached and there is no `logs` verb.** `docker compose up` attaches to the containers' output; a cluster-wide log stream needs the log broker (SWK §19), which is deferred, so `-d` is accepted and is a no-op. `satl compose ps` is the project-scoped task list (the names are namespaced, so `satl service ps` would mean reconstructing them by hand). **`satl compose config` prints the resolved *specs* as JSON**, not the merged compose file as docker does: the namespaced names, the aliases, the project labels, the nanosecond durations and the ingress ports are where the surprises are, and it is what `up` will post. `--quiet` validates and prints nothing. Absent by design: `build`, `pull`, `run`, `exec`, `restart`, `stop`/`start`, `top`, `events`, `--wait`, `--profile`. |

## Published ports and health (M5)

`pf` does not probe a `rdr` pool -- it is a packet filter, so a container that stops
answering keeps its share of the traffic until something upstream removes it. What
removes it is the task being stopped and `FAILED` (#88), after which the node's
level-triggered port pass rewrites the whole anchor without it. Detection latency is
therefore the whole exposure, and Docker's probe defaults (30 s interval, 3 retries) put
it at about 90 s. Docker Swarm's routing mesh has the same architecture -- IPVS does not
probe backends either -- so the difference is numbers, not machinery, and the numbers are
what these entries change. **Measured** on this host, end to end (`satld/tests/health_pool.rs`):
9.97 s from the probe starting to fail to the address leaving the `satl/rdr` anchor.

| # | Deviation |
|---|---|
| 125 | **A service that publishes a port gets tighter probe defaults than Docker's**, and only there: `interval` 5 s instead of 30 s and `retries` 2 instead of 3, applied **field by field and only where the healthcheck left the field unset** (0 or absent, Docker's own "unset" spelling). An explicitly set value always wins, so Docker's behaviour is available by asking for it (`Interval: 30000000000`, `Retries: 3`); a service that publishes nothing keeps Docker's defaults untouched, and so does a `start_period`, which is a property of the workload's boot time rather than of the pool. Docker applies its defaults identically whatever the service publishes, and applies them *at probe time*, leaving the stored spec exactly as posted. SatL instead **writes the values into the stored spec** at create and update, so `satl service inspect` shows the numbers the prober will use instead of a zero that means something else, and logs one line naming them (`tighter health probe defaults applied to a published service ... applied=interval=5s timeout=3s retries=2`). The consequence to know is that they then look explicit: removing the published port later does not restore Docker's 30 s, because nothing can tell an operator's `5s` from ours. The trade this buys, and its cost, are in `docs/operations.md` ("Published ports and healthchecks"): in SatL an unhealthy task is *stopped* (#88), so a ninefold faster detection is also a ninefold more eager replacement. |
| 126 | **The per-probe `timeout` of a published service is never longer than its `interval`.** Docker's default is 30 s for both, which is coherent at a 30 s interval and nonsense at a 5 s one -- and the failure is silent rather than loud: the prober runs one probe at a time (as moby's `monitor` does, resetting its interval timer only after the probe returns), so an oversized timeout does not overlap or queue probes, it stretches the detection bound to `retries x (interval + timeout)` with nothing in the configuration looking wrong. A hanging probe on 5 s/30 s/2 takes 70 s to a verdict, not 10 s. So, for a published service that left `timeout` unset: **3 s** when the `interval` was also unset (SatL owns the cadence; 2 s of headroom under the 5 s interval covers `ocijail exec` on a loaded box), and **`min(30 s, interval)`** when the interval was set explicitly -- Docker's own value, capped at one cycle, because an operator who chose a 2-minute interval chose the latency and tightening their timeout could only fail a slow probe that Docker would have passed. Unpublished services are untouched: 30 s/30 s, exactly Docker. |
| 127 | **`POST /containers/create` reads no healthcheck at all**, so a published *container* is never health-gated: `Config.Healthcheck` (docker's `--health-cmd` and friends) is accepted by the JSON parser and dropped, the anonymous service is created with none, and `satl run` has no `--health-cmd` to set one with. The consequence is the one #125 exists to bound, unbounded: the redirect is installed as soon as the jail starts -- measured at 5 ms after jail start, against the 250 ms nginx needs to bind -- and it is never removed for a container that stops answering while its jail stays up. Only the **service** path (`POST /services/create`, `satl service create` over the REST API, compose's `healthcheck:`) honours a healthcheck, which is where the missing-probe warning is raised; `satl run -p` is deliberately *not* warned, because there would be no way to comply and a warning nobody can act on is how a warning that matters gets ignored. Docker gates nothing on health either (`--restart` ignores it), but it does at least run the probe and report `State.Health`. Plumbing `Config.Healthcheck` through the container API, and the six `satl run --health-*` flags, is its own change. |
| 128 | **A published service with no healthcheck at all is a warning at create and update**, in the `Warnings` array of `POST /services/create` (so `satl service create` prints it) and in the log: `service web publishes 8080->80/tcp and has no healthcheck: its tasks are published as soon as the jail starts, before the workload can answer, and stay published while a dead container keeps its share of the traffic`. Docker warns about nothing here -- its `Warnings` carry image-resolution notes -- and SatL does not refuse either: a service with no probe is legitimate (an operator may health-check the port from a load balancer instead), it is just not what the publisher usually means. "No healthcheck" includes every form that runs no probe: absent, `["NONE"]`, `[""]` (#91), a bare `["CMD"]`, and an unrecognized `Test[0]`, which Docker also merely warns about. |

## System prune and layer GC (M5)

Until M5 nothing reclaimed anything: `grep` for `fn gc`, `fn prune`, `unreferenced` or
`refcount` across `satl-storage` returned nothing, so unused image layers and their
datasets grew without bound and hand-deleting a dataset was not a remedy because nothing
reconciled it. `satl system prune` closes that, with Docker's shape verified against
`docker system prune --help` on this host (docker-cli 29.4.2) rather than recalled.

Two SatL facts shape every entry below. **A container is a task of a service**
(invariant #2), so pruning one cannot mean what it means in Docker; and **layers, blobs
and volumes live on one node**, so a prune answered by one daemon reclaims one node.

| # | Deviation |
|---|---|
| 129 | **Pruning a stopped container removes the service backing it**, exactly as `satl rm` does (#33) -- and with it the jail, the epair and the rootfs dataset that container still holds. There is no other coherent answer: leaving the service would have the orchestrator refill the slot the moment the reaper freed it, so "prune the container" would *create* one. The safety rail is at the service, not at the container: a service is pruned only when **every** container of it is stopped, so a `--replicas 3` service with one dead task keeps all three. Docker's `container prune` never touches anything above the container because it has nothing above the container. |
| 130 | **Images, layers, blobs and volumes are reclaimed on the answering node only; containers and networks are cluster-wide.** That asymmetry is what SatL is -- a task and a network are store objects, an image layer is a ZFS dataset on whichever node pulled it -- and it is the one thing an operator can most easily get wrong, so both the confirmation prompt and the summary name the node (`Total reclaimed space: 62.34MB (on alpha; images, layers and volumes are node-local)`) and say to run it on every node. Docker has no cluster to be wrong about. The per-object prune verbs (#163) repeat that statement in the same words, from the same helper. |
| 131 | **`POST /images/prune` never destroys a layer on the strength of one reading**, and its response carries a `Deferred` array Docker has no equivalent for. A layer dataset is destroyed only when **two consecutive passes** agree it is unreferenced (1.5 s apart, within the one request), because the claim set is assembled from readings that are each momentarily incomplete at different times -- the store just after a leadership change, a worker just after a restart, the image store mid-pull. What the second pass disagreed about is reported rather than silently skipped, with `satl system prune` printing `N layer(s) were unreferenced on only one of the two passes ... Run prune again to reclaim them`, so a prune that reclaimed less than expected is explicable. Same discipline, and same reason, as the periodic dataset sweep (`27ccb64`). Since M9 the same two passes run **inside `DELETE /images/{name}`** as well (#155), which is why a single `satl images rm` takes about a second and a half: a targeted removal has no more right to one reading than a prune does. |
| 132 | **There are no dangling image *records* to delete, so "dangling" means unreferenced content.** `repositories.json` maps a canonical reference to digests and nothing else, so an image with no reference simply has no record and `<none>:<none>` is unrepresentable (which is also why `satl images` never prints it). What a re-pulled tag leaves behind is therefore blobs, manifests and configs that nothing reaches -- and that is what a prune without `-a` reclaims, reported as `deleted: blob:sha256:...` / `manifest:` / `config:`. `-a` additionally forgets every image record no task's spec asks for, reported as Docker's `Untagged`. `DELETE /images/{name}` is the same two things scoped to one target: it reports `Untagged` for the `repositories.json` entry it forgot and `Deleted` for whatever layer datasets and content files stopped being reachable as a result (#155). |
| 133 | **A pull in flight stops content reclamation for that pass, and says so.** A blob is written before the `repositories.json` entry that names it, so while any pull holds its per-reference lock the reachable set is incomplete *by construction* and nothing may be deleted on that reading. The layer half is protected differently and does not have to stop: an image record exists before the datasets it describes, and a chain mid-apply is claimed by the layer store's own gate. |
| 134 | **`--filter` is absent and an unknown filter is a `400`, not a silent no-op.** The only filter understood is `dangling` on `/images/prune`, because that is how `-a` reaches the daemon (`filters={"dangling":["false"]}`; both of Docker's encodings of a filter map are accepted). `until=` and `label=` change *what gets deleted*, so accepting and ignoring them would delete more than the caller asked for -- the one compatibility shortcut that cannot be taken with a command whose job is destroying things. |
| 135 | ~~**`satl system prune` is the only prune verb**~~ **superseded by #163 (M9).** `satl images prune`, `satl container prune`, `satl network prune` and `satl volume prune` now each drive the endpoint they already had, and `satl system prune` remains the one that drives all four in Docker's order. The rest of this entry still holds. `-a/--all`, `--volumes` and `-f/--force` are Docker's, the confirmation prompt is Docker's, and it is the first prompt in the CLI -- everything else `satl` does is non-interactive. A `y`/`yes` answer (case-insensitive) proceeds; **anything else, including a stdin that cannot be read at all, declines**, because a prune that went ahead because it could not ask would be the worst possible reading of silence. #72's "no `prune`" for `satl network` still holds as a *CLI* statement. |
| 136 | **`SpaceReclaimed` for containers is measured before removal and can be short of the truth.** A container rootfs cannot be destroyed while its jail is still dying (up to 2 x `net.inet.tcp.msl`, `docs/jail-teardown.md`), so prune reports the bytes those datasets held when it looked, and the node's periodic dataset sweep is what actually frees them within about a minute. The alternative -- waiting -- would make prune take a minute per stopped container. Docker has no dying-prison problem and no discrepancy to report. |

## Backup and restore (M5)

Procedures, measurements and the failure signatures are in `docs/operations.md`,
"Backup and restore". These are the API-visible consequences.

| # | Deviation |
|---|---|
| 137 | **`ForceNewCluster` is `501`, permanently, not "not yet".** Docker rebuilds a swarm from one surviving manager's raft state by discarding the other members; SatL refuses because neither half of that is a thing it needs. A manager that still has its raft directory resumes on a plain `satld` restart, and one that has lost it has nothing to force *from* -- the recovery is a restore of `<state_dir>/raft` (the `dek` included) or, on a cluster with other managers, discarding this node's identity and re-joining, which was measured at 6 s end to end. The 501 body says all of that and points at `docs/operations.md`. Entry #42's "(M5 disaster recovery)" is settled by this one. |
| 138 | **A manager certificate over an empty raft directory makes `satld` refuse to start**, where dockerd would come up as an ordinary non-swarm node. First boot writes the raft state *before* minting a certificate against the cluster id it seeds there, so that combination is never a first boot -- it is state that was lost, or a restore that has not been done yet. Self-initializing would mint a second cluster under the same certificate, empty, with a new cluster id and no root CA, and it would look healthy while every service, secret and network was gone. The error names both recoveries. (A worker's equivalent -- a certificate with no `managers.json` -- has refused since M4.) |
| 139 | **A raft directory whose `dek` is missing is refused, rather than re-keyed.** `satld` will not create a data encryption key beside sealed data: the log and the snapshot cannot be read without the original, and a new key would make the state unreadable for good, so a restore that forgot one file is an error message instead of a silent loss. Docker has no per-manager at-rest key by default (its autolock is opt-in), so it has no equivalent. Lax permissions (`0640`) and a wrong-length key are refused the same way. |

## Metrics (M6)

The Prometheus surface is not part of the Docker Engine API, but its names are
a compatibility contract of their own: off-the-shelf Docker dashboards query
dockerd's series by name.

| # | Deviation |
|---|---|
| 140 | **The namespace is split, not uniform.** Where dockerd defines a series SatL has an equivalent of, SatL emits Docker's exact name -- `engine_daemon_container_states_containers`, `engine_daemon_health_checks_total`, `engine_daemon_health_checks_failed_total`, `engine_daemon_engine_info`, `engine_daemon_engine_cpus_cpus`, `engine_daemon_engine_memory_bytes` and the `http_requests_total` API histogram (method/code labels, lowercased method, as Docker's) -- so existing Docker dashboards render unchanged. Everything SatL-specific is `satl_*`: raft state, store counts, reconcile passes, dispatcher sessions, external-command failures, certificate expiry, per-task rctl usage. One name per fact, no duplicate series. `docs/architecture.md` §16's original `satl_*`-for-everything commitment is amended accordingly. |
| 141 | **`/metrics` is a separate listener, off by default, and unauthenticated** -- dockerd's exact posture (`--metrics-addr`). | 142 | **Per-container usage comes from rctl, and exists only when `kern.racct.enable=1`.** `satl_container_memory_usage_bytes` and `satl_container_cpu_time_seconds` (rctl `memoryuse`/`cputime`) are read on the 20 s collector cadence, one series set per running task, pruned to the live set each pass -- with racct off no `rctl` process is ever spawned and the series are simply absent, the same degradation `--memory`/`--cpus` already accepts. Docker's per-container Prometheus series need cAdvisor beside the daemon; SatL's need nothing but the kernel accounting the node already has. |

## PROXY-protocol publish mode (M6)

| # | Deviation |
|---|---|
| 143 | **`satl.publish.proxy_protocol=v2` on a service opts its published TCP ports into a userspace L4 proxy.** Docker's `PublishMode` has only `host` and `ingress`, and unknown spec fields are a 400 (#50), so the opt-in is a label, Docker itself would just ignore it. On a labeled port, `satld` listens on the published port (every manager, like the mesh), picks a healthy task from the same set that feeds the pf pool, dials it over the overlay and writes a PROXY protocol v2 header before splicing: the task sees the **real client address**, which the pf mesh's return-path SNAT destroys (#75). ## Building images (M6)

| # | Deviation |
|---|---|
| 144 | **`satl build` is not `POST /build`, and a `Satlfile` is not a Dockerfile.** Docker's build runs in the daemon from a Dockerfile context; SatL's runs client-side on the node's host, reads a line-based pkg-oriented file (`FROM` (multiple, with `AS` for multi-stage, or `scratch`), `PKG`, `COPY` (including `--from=<stage>`), `RUN`, `ENV`, `LABEL`, `WORKDIR`, `EXPOSE`, exec-form `ENTRYPOINT`/`CMD`), and registers the result in the local content store through `satl-image`. Since M8b the image is multi-layered, base layers plus one layer per mutating step, diffed with whiteouts, and a content-addressed cache in `/var/db/satl/build-cache/` skips unchanged steps (`--no-cache`, `--cache-dir`). The build context is the Satlfile's own directory (no positional `PATH`); `RUN` executes in a chroot of the assembled rootfs on the build host's kernel (M7b). The REST API has no build endpoint; Docker clients building against satld get a 404 on `POST /build`. The image lands in the local node's store only, multi-node deployments build per node or push to a shared registry. |
| 145 | **Jail parameters are set by container label, not by `--sysctl` or a daemon flag.** Docker exposes kernel knobs per container (`--sysctl`, `--cap-add`); SatL's equivalent surface is the jail, and the escape hatch is a label: `satl.jail.<param>=<value>` on a container (`--label`, or compose `services.x.labels`) becomes the OCI annotation `org.freebsd.jail.<param>=<value>` that ocijail already understands (docs/ocijail.md §2.2). The motivating case is SysV IPC, a jail disables it by default and PostgreSQL cannot even `initdb` without `sysvshm`/`sysvsem`, so `satl.jail.sysvshm=new` + `satl.jail.sysvsem=new` are the documented recipe. Unknown parameters are warned about and ignored by ocijail. There is no privilege boundary here: whoever can create containers can already bind-mount the host into a root-owned jail. |
| 146 | **`kill` on a service task retires the slot; the service is *not* brought back to N/N.** Docker's `docker kill` signals the container and never touches the task's desired state, the task fails, the restart supervisor replaces it. SatL's kill (#31) writes `desired=shutdown` to the store, which is the intentional-stop state: the supervisor only restarts terminal tasks whose desired is `running`, and the replicated orchestrator never refills a slot that still holds stopped tasks, so the service sits at 0/N until the spec changes or it is scaled away and back. Matching Docker needs an agent-side signal channel that does not exist yet. Until then, the documented way to rehearse a container crash is to kill the jail on the host (`jail -r`), which the agent reports as a terminal task against `desired=running`, and the replacement comes. |
| 147 | **A resources-only `service update` is a hot resize, not a roll.** Docker Swarm replaces every task on any spec change; per-container vertical scaling lives in a different verb entirely (`POST /containers/{id}/update`, which SatL does not have, there are no standalone containers, #80). SatL instead detects an update whose only task-spec difference is `Resources` (limits and/or reservations), leaves every task running and pushes the new values into the task objects; each node's agent then re-writes the jail's rctl rules in place (old rules removed first, `rctl -a` stacks same-subject rules instead of replacing them, measured on 15.1). A memory shrink below the jail's current usage arms the `memoryuse:sigkill` rule under the watermark, the task is not killed preemptively, but the agent logs a loud warning naming the kill that may follow, and with racct off the resize degrades to "accepted, not enforced" exactly like limits at create (§8.3). Any other field in the diff, image, env, one label, takes the ordinary rolling path and the replacement carries the new resources whole. |
| 148 | **`satl stack` exists, and it is the compose machinery under Docker's verb names.** `deploy` is `compose up` (one file, no merging; the stack name is the project name), `rm` is `compose down`, `config` is `compose config`, and `ls`/`services`/`ps` read the project label (`com.docker.compose.project`) off the services, there is no `com.docker.stack.namespace` label, and no server-side stack object. `--prune` defaults true, as Docker's `stack deploy` (compose's `up` keeps its explicit `--remove-orphans`); `--resolve-image` and `--with-registry-auth` are not implemented. An unknown stack is a CLI-side `nothing found in stack <name>`, Docker asks the daemon, SatL filters client-side, so the error comes from the CLI, not the API. |
| 149 | **Placement preferences rank, they do not filter.** `spread=<descriptor>` (Docker's only strategy, and SatL's) reorders the scheduler's candidates after the fault penalty and before the per-service spread: the node whose descriptor-value group holds fewer of the service's tasks wins. Nodes missing the label form one empty-value group, as Docker's. Multiple preferences apply in spec order. Nothing is enforced, a preference never makes a node ineligible, so a one-group cluster schedules exactly as before. |
| 150 | **Jobs run to completion, with SwarmKit's semantics and three stated gaps.** `ReplicatedJob` keeps at most `MaxConcurrent` tasks live until `TotalCompletions` slots have exited 0 (both default 1; the CLI's `--replicas` sets both); `GlobalJob` runs once per eligible node, and a node that becomes eligible later gets its run. A `Complete` task is never restarted, anywhere; a failed one is retried in its slot within `MaxAttempts`, created **immediately**, no restart-delay queue (a job has no caller to pace), and `Restart.Window` is not honoured (the budget is the slot's lifetime, not a rate). A spec update re-runs the job: no rolling, no `update_status`. `service ls`'s `REPLICAS` shows completions-over-goal (`2/3`); `JobIteration` is not rendered (the store's `spec_version` plays that role). |
| 151 | **Manager autolock is per-manager at boot, cluster-wide by the store.** `swarm init --autolock` / `swarm update --autolock=` flips `EncryptionConfig.AutoLockManagers`; each manager then seals its raft DEK under the cluster unlock key (32 random bytes, base64, printed once) and deletes the plain file, the key itself lives only in the DEK-encrypted store, Docker's own circular construction. A locked manager serves only `GET /_ping` and `POST /swarm/unlock` on its API socket (everything else: 503 "this swarm manager is locked") until the right key arrives (401 on a wrong one); the DEK exists only in memory after that. `swarm unlock-key` prints it, `--rotate` replaces it and every manager reseals. Workers never lock (no raft log). A locked manager restored from backup still needs the key, back up `dek.sealed` *and* the unlock key, or the restore is a paperweight. |
| 152 | **`satl push` is client-side; `POST /images/{name}/push` is a 404.** Docker's push runs in the daemon because dockerd owns the store; SatL's store is the node's local one and the push reads it directly from the host, the same split as `satl build` (#144), with the same consequence: a Docker client pushing against satld's API gets 404. The push uploads only the blobs the registry lacks (HEAD per blob), then the manifest; credentials come from `--username` + `--password-stdin`, never stored. `satl build --push` is the one-command form. |
| 153 | **An absent `TaskTemplate.RestartPolicy.Delay` is filled with the 5 s SwarmKit default at admission, even when the rest of the policy is present.** Docker's CLI applies the same default client-side; a client that sends `{"Condition":"on-failure"}` and no `Delay`, compose's `deploy.restart_policy` without `delay:`, `satl service create --restart-condition`, used to have the zero stored verbatim, and a crash-looping service then restarted with no pause at all (measured: ~110 failed tasks/minute for 3 replicas, each attempt a jail + ZFS clone + epair). Absent `MaxAttempts`/`Window` stay 0 (unbounded), as Docker's. One caveat the wire forces: `Delay` is a plain integer, so an explicit `"Delay": 0` is indistinguishable from an absent one and becomes 5 s too, a zero-delay restart is not expressible. |

## Removing images, and the verbs that were missing (M9)

An audit of the whole surface found five capabilities the daemon has served since M1-M2 with
**no CLI client at all**, and one operation missing at both layers: there was no way to delete
a single image, from `satl` or from a Docker client. This section is what closing that changed.

| # | Deviation |
|---|---|
| 154 | **`satl images` is a noun with subcommands, which `docker images` is not.** Docker spells these `docker image rm` / `docker image prune` / `docker image inspect` and keeps `docker images` a pure listing with an optional positional `[REPOSITORY[:TAG]]` filter, a subcommand name there would be ambiguous with an image called `rm`. `satl images` has never taken a positional, so the noun is free: `satl images ls|rm|prune|inspect`, with bare `satl images` keeping Docker's listing and its `--no-trunc`/`-q` byte for byte. `satl rmi` is kept as a top-level alias of `satl images rm`, which is what Docker does with its own legacy `rmi`; it is a second CLI entry point onto one implementation, because a clap alias on a noun cannot reach a subcommand of it. The standing cost, recorded because it is a door closing: **`satl images` can never gain Docker's positional repository filter** without colliding with these names, and an image literally named `rm`, `ls`, `prune` or `inspect` must be addressed with its tag (`satl images rm rm:latest`). |
| 155 | **`DELETE /images/{name}?force=&noprune=` runs a full prune inside the request, and it costs about 1.5 s.** Docker's rmi untags and then deletes whatever the untag orphaned, in one pass. SatL cannot: a layer's loss is recoverable only from a registry that may not answer, so #131's two-agreeing-passes rule applies to *every* path that destroys a layer, not only to prune. The request untags the record (`ImageStore::remove`, which writes `repositories.json` before anything else, #132), then takes two layer readings 1.5 s apart and destroys only the chains both agree are unreferenced, then sweeps unreachable content. The response is Docker's array of `{"Untagged"}`/`{"Deleted"}` items. `?noprune=1` skips both sweeps and is the way to pay that cost once for a batch rather than once per image; Docker's meaning for the flag, keep untagged *parent* images, has no analogue, because SatL images have no parents (#41). |
| 156 | **What the layer sweep deferred rides on `X-Satl-Deferred-Layers`.** Docker's rmi response is a bare JSON array with no field for it, and a third field on the item would corrupt a real Docker client's output: moby's rmi loop prints `Untagged: ` for an item with neither field set. So the count travels as a response header, invisible to a Docker client, read by `satl images rm` to print the same "run again" sentence `satl system prune` prints, from the same helper. The chains themselves stay in the daemon log, where `collect_layers` already names them. |
| 157 | **Six path words are reserved on a `DELETE` tail.** An image name carries slashes, so the whole `/images/{name}/*` family is one tail-wildcard route dispatched on the method first: `POST …/tag`, `GET …/json` and a bare `DELETE` are served, everything else keeps the fallback's `page not found`. The price is stated rather than hidden: a `DELETE` whose tail's **last path segment** is exactly `tag`, `json`, `push`, `history`, `get` or `load`, **with at least one segment before it**, is read as an unimplemented sub-verb and answers 404 instead of removing an image by that name. A repository whose last component is one of those words is still removable, spell the tag (`DELETE /images/team/get:latest`). A bare tail is always a name, so an image simply called `get` is unaffected. Docker, which registers `DELETE /images/{name:.*}` and has no DELETE sub-verbs, would answer `No such image` instead; both are 404s with different messages. |
| 158 | **Removal by image ID is supported, and the ID form is recognised *before* the reference parser.** SatL's image ID is the manifest digest (#41), so `satl images rm sha256:<hex>`, or a bare hex prefix of at least six characters, with or without the `sha256:` prefix, selects every record whose digest matches. The ordering is load-bearing, not a detail: `sha256:abcdef` is a *syntactically valid* Docker reference (`docker.io/library/sha256:abcdef`), so parsing first would turn every removal by ID into a lookup that can only miss. A bare hex run is only read as an ID when it carries no `:`, `/`, `@` or `.`, which keeps `deadbeef:latest` addressable as a name. |
| 159 | **An image reachable from several references must be forced.** Removing by ID when two tags resolve to the same manifest digest would forget both, which is not what an unqualified request means, so it is a `409 conflict: unable to delete <id> (must be forced) - image is referenced in multiple repositories`, Docker's rule and Docker's wording. `--force` untags all of them. |
| 160 | **`GET /images/{name}/json` aggregates by image ID; `GET /images/json` does not.** The store is keyed by reference, so the listing has one row per reference (#15) while inspect takes Docker's view: one document per image ID, `RepoTags` listing every reference that resolves to it, which is what makes #159's message legible. Gaps against Docker's `ImageInspect`, all structural rather than unfinished: `Config.Labels` is always `null` (the image config parser does not read a `Labels` block, so an empty map would claim the image declares none); `Parent`, `Comment`, `Author` and `DockerVersion` are empty (#41); `Size`/`VirtualSize` are the sum of the **compressed** manifest layer sizes, where Docker's is the uncompressed rootfs, exactly as `/images/json` already reports them; `Container`/`ContainerConfig` are absent (deprecated upstream); `GraphDriver` is always `{"Name":"zfs","Data":null}` (invariant #5); and `Platform` is the SatL extension (#15). |
| 161 | **Image-in-use is decided once, and a live claim cannot be forced.** `DELETE /images/{name}` and the `-a` half of `POST /images/prune` ask the same function the same question, so the two verbs can never disagree about what is in use. A **non-terminal task** referencing the image, or **any service spec** referencing it, is a `409 … (cannot be forced)` that `--force` does not override, a service spec is a standing order to create tasks, and untagging under it turns the next start into a pull against a registry that may be gone. Only-terminal references are a `409 … (must force)` that `--force` untags anyway; Docker draws the line in exactly these two places. Comparison is on the canonical reference **both ways** (a record is keyed `docker.io/library/alpine:latest` while a spec may say `alpine`), and a task spec whose image reference **will not parse** makes every removal a `cannot be forced` conflict, the claim set is then incomplete by construction, which is the same fail-safe `images prune` has always had, now expressed once instead of twice. Every message names the image and the container or service, never a spec payload. On a node with no manager the claim set comes from the local task DB rather than the store, so **image removal never answers 503**, unlike `satl node ps` (#164), which is cluster state and does. |
| 162 | **`satl events`' flags are honoured, refused, or sent with a warning, never forwarded to be silently ignored.** `--since` is **sent** and the CLI prints one line on stderr saying nothing before it will be replayed, because the daemon accepts the parameter and discards it (#37): SatL's watch feed keeps no history. Refusing the flag outright would break a line copied from `docker events`; forwarding it in silence would let an operator believe in a replay that never happened. `--until` is sent and gets the route's existing `501`, which names the parameter and comes from the component that owns the refusal. `--filter` is applied **client-side** on the parsed event (`type`, `event`, `container`, `image`, `label`, `scope`) because the daemon does not read `filters` at all (#21), so the whole stream crosses the socket and the CLI drops what does not match; an unsupported key is refused **before the connection is opened**, the rule #134 sets for every selective flag. `--format` accepts `json` (the daemon's NDJSON line, verbatim) and refuses a Go template: there is no template engine in `satl`, and half of one is worse than none. Event timestamps render in **UTC with a `Z`**, in Go's fixed nine-digit `RFC3339Nano` layout, where Docker prints the local offset, `satl-cli` has no timezone database and `unsafe_code = "deny"` rules out `localtime_r`. |
| 163 | **The four prune endpoints each get their own CLI verb, superseding #135.** `satl images prune [-a]`, `satl container prune`, `satl network prune` and `satl volume prune` drive exactly the endpoints `satl system prune` has always driven, with the same semantics, the same `-f/--force`, and the same confirmation prompt read the same way (#135's reading of silence still stands). `satl container` is a **new noun holding only `prune`**: SatL's container lifecycle verbs stay top-level (`satl ps`, `satl rm`, `satl stop`) because Docker's container surface is flat and a second spelling of a verb that already has one is only a second thing to keep in sync, the noun exists for verbs with no flat spelling at all. Every verb that reclaims disk ends on #130's node-local sentence, from one helper; `satl network prune` is the one that does not, because a network is not disk and there is no space to report. |
| 164 | **`satl node ps` defaults to `self`, and it is manager-only.** Docker's default is the same. The reference resolves through `GET /info` when it is the literal `self`, as `satl node inspect self` already does, and the tasks come from `GET /tasks?filters={"node":…}`, which matches a node ID prefix or an exact hostname (#47). That filter is served from the Raft store, so `satl node ps` on a worker gets the standard `503 This node is not a swarm manager`, the asymmetry with image removal (#161) is the point: one is cluster state, the other is node-local. |
| 165 | **`satl info` prints only what `GET /info` can source.** Docker's `docker info` block for Logging Driver, Cgroup Driver/Version, Runtimes, Default Runtime, Init Binary, Security Options, Registry, Live Restore, Kernel Version, Docker Root Dir and the plugin lists is **omitted rather than printed empty**: `/info` has never served those fields (the M0 daemon-wide table), and a zero or an empty string in that layout reads as a configured value rather than an absent one. `Storage Driver` is always `zfs` (invariant #5) and `OSType` is `freebsd`. The `Swarm` block's `Nodes`/`Managers`/`Node Address` are likewise omitted on a worker, which genuinely does not know them (#46). `Total Memory` is rendered in decimal units by `format::human_size`, Docker's `units.HumanSize`, where `docker info` uses binary `GiB`, one size formatter for the whole CLI beats two that disagree. |
| 166 | **The API surface is published as a generated OpenAPI 3.1 document, and it is a file, not an endpoint.** `docs/openapi.yaml` is generated from the `#[utoipa::path]` annotations on the handlers and `make check` fails when it drifts from the code; `docs/api.html` renders it offline from a vendored Redoc bundle. The daemon serves neither, invariant #8 says the Docker REST API is the only external surface, and a `/swagger` route would not be part of it. Two things the document states that the routes do not literally say: `POST /images/{name}/tag`, `GET /images/{name}/json` and `DELETE /images/{name}` appear as ordinary paths although the daemon routes them through a tail wildcard, and `{name}`'s slashes may be sent raw or percent-encoded because axum decodes path captures before the handler sees them. Routes api-compat #22 keeps at 404 have no operation in the document at all. |

## Field fixes (M10)

Defects found by running the documented commands against a live cluster, each with a
Docker-behavior consequence worth recording.

| # | Deviation |
|---|---|
| 167 | **A foreground `satl run` whose task is rejected before it ever starts removes the container it just created; a detached one does not.** Docker never has this window: its CLI pulls before create, so an unresolvable image fails with no container. SatL resolves the image on the assigned node (a manager holds no manifest), so the failure is structurally post-create. The foreground CLI restores Docker's observable outcome by deleting the anonymous service after printing the daemon's error; `satl run -d` has already exited, so the dead container stays visible in `satl ps -a` and is removed with `satl rm`. In the same change `POST /containers/{id}/wait` stopped filling `Error` for a container that ran and exited non-zero, which is Docker's contract: `Error` reports wait failures, and a task whose container status carries an exit code answers with `StatusCode` alone. Before this a foreground run of a failing container reported a daemon error instead of the container's own exit code. |
